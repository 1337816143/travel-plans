# ADR-0002：青岛 Phase 4 内容治理、模块与可编辑预设

- 状态：接受（候选内容仍待人工审核）
- 日期：2026-08-02
- 范围：仅 `1337816143/travel-plans` 的青岛 v3 sidecar

## 背景

v2.5.4 把 49 个运行时点位、固定 8 日路线、来源、预约、酒店、推荐和愿望清单保存在多组 Legacy JS 数据中。它们是必须保留的迁移基线，但稳定攻略、季节信息、动态观察和实时结果尚未形成统一发布边界。Phase 3 的四个演示模块也不足以表达多种青岛旅行方案。

内容研究不能通过“抓到一条网页信息就自动发布”完成。开放时间、票价、预约、班次、浴场状态、天气、路况、价格和库存都可能变化；社交与商业平台还存在推广、门店错配和排序偏差。因此 Phase 4 必须先建立可审计候选包和人工发布门禁。

## 决策

### 1. 单一青岛内容目录

建立 `ContentCatalog` 作为青岛内容包入口，当前候选包固定包含：

| 类型                 | 数量 | 当前状态                                       |
| -------------------- | ---: | ---------------------------------------------- |
| v2.5.4 运行时点位 ID |   49 | 全部保留；内容仍为 `review-required`           |
| 目录来源             |   42 | 11研究＋24 Legacy＋7服务；均 `review-required` |
| Legacy 内容快照      | 1 套 | 24／8／3／17／10／12 只读对账                  |
| 季节信息             |    4 | `review-required`，均明确是否需运行时复核      |
| 日程模块             |   17 | `review-required`，可拆改、可组合              |
| 可编辑预设           |   17 | `review-required`，含唯一原版 8 日方案         |
| 预约规则             |   11 | 3治理规则＋8 Legacy 规则，带来源与动态边界     |
| 酒店／愿望候选       | 3/29 | 原字段完整保留，不升级动态评分、库存或营业状态 |
| 服务点候选           |    7 | 3个医院锚点＋4类运行时查询，不计入正式49点     |
| 更新任务             |    5 | 只生成待审候选，不自动发布                     |
| 研究／迁移批次       |    2 | `review-required`，均保留未解冲突              |

目录只保存青岛实体，不接受国家、全球城市或跨国目的地层级。

### 2. 四层信息边界

1. 稳定攻略：名称、位置、类别、长期体验与推荐停留；版本化发布。
2. 季节信息：适用月份／日期范围、来源和运行时复核要求。
3. 动态观察：必须保存来源、观测时间、TTL、新鲜度、置信度与审核状态。
4. 实时信息：天气、路况、班次、库存和当日价格只由运行时 Provider 返回。

`ContentUpdateJob` 只是检查契约。无论由 GitHub Actions、Serverless 还是人工执行，变化结果都必须进入新批次并停在 `review-required`，不能直接改正式内容。

### 3. 人工审核状态机

内容批次采用以下显式转换：

```text
draft → researching → imported → validating → review-required
                                                ├→ approved → published → rolled-back
                                                └→ rejected → draft
```

`approved` 必须有审核人、审核时间且没有未解冲突；`published` 还必须有发布版本。当前候选包故意保留冲突和空审核人，因此 `createContentRelease` 必须失败。测试只用模拟人工签名的克隆验证发布／回滚算法，不修改候选数据状态。

### 4. 预设是 Planner 输入，不是固定页面

17 套预设由 `dayAssignments + moduleIds + selectionPriorities` 表达。`generateTripPlanFromPreset`：

- 校验 TripRequest 天数与预设一致；
- 按日模块确定初始点位顺序；
- 尊重用户 `exclude`；
- 对预设外必去项输出可解释冲突；
- 仍生成标准 `TripPlan`，继续支持 Phase 3 的拖动、批量、锁定、Undo／Redo、保存、导入导出和样式系统。

“原版青岛 8 日舒适旅行方案”恢复 v2.5.4 的八日日级主题和核心路线点；Legacy 的完整逐项时间轴、原文说明和 Plan B 仍由正式 v2.5.4 页面提供，待后续无损内容迁移门禁完成。

### 5. 来源和推广风险

政府与官方运营方优先。地图、商业平台和社交媒体只作为核验或体验线索。社交来源必须记录 `promotionalRisk`、独立证据数、审核笔记和冲突标志；高风险且无独立证据的内容不能独立成为正式推荐。

### 6. Legacy 内容使用生成快照而非手工复制

`scripts/snapshot-v2-content.mjs` 从四个 canonical Legacy 模块生成只读 JSON。CI 每次重新计算并比较快照，数量固定对账为 24 项来源、8 项预约、3 家酒店、17 项必去、10 个愿望地图点和 12 项必吃必买。新目录保留每条原始记录，并在其外增加审核状态、来源映射和运行时复核边界；构建或验证不得修改 Legacy 源码。

### 7. 服务点先做候选层

医疗候选以官方院区地址和地图坐标交叉核验，并在进入内部模型前转换为 WGS84。药店、厕所、停车和充电的营业、库存、空位、接口和可用性高度动态，因此只保存运行时查询规则，不创建假地点。危急医疗场景明确优先拨打120，不让直线距离排序替代急救调度。

## 影响

### 正面

- 内容、Planner 和 Web 使用同一运行时 Schema；交叉引用和数量在加载时失败而非静默漂移。
- 原版 8 日和专题预设均可直接生成可编辑计划。
- 动态事实不会被候选研究自动升级为正式事实。
- 发布与回滚有独立 manifest 和测试证据。

### 代价与未完成项

- 当前 49 点不是“青岛完整攻略库”；医院、药店、卫生间、停车、充电仍只是旁路候选，尚未成为正式点位。
- v2.5.4 的 24 项来源、8 项预约、3 家酒店、17 项必去和 12 项必吃必买已无损迁入候选目录，但尚未获得人工审核签名。
- Legacy 逐日完整时间轴、攻略正文、Plan B 和用户状态仍未全部转为可替代 v2.5.4 的正式内容包。
- 五个更新任务尚未绑定调度平台；真实路线、天气、票务和库存 Provider 仍未接入。
- 没有人工审核人，因此不得把 Phase 4 候选称为正式发布内容。

## 回滚

v3 sidecar 没有被根 `index.html`、GitHub Pages 或 Service Worker 引用。回滚时撤销 Phase 4 的 Schema、`@qingdao/content`、预设 Planner、Web 展示和测试即可；v2.5.4、`src-v2/`、v1.0.15 以及正式 Pages 均无需改动。若未来内容包已发布，则用 `ContentReleaseManifest.rollbackTargetVersion` 恢复上一内容版本，不能删除历史批次。
